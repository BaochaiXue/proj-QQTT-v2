Warmup A

普通 warmup：让 live pipeline 先站稳

它解决什么

普通 warmup 的目标是把相机、FFS depth、SAM3.1/EdgeTAM mask、 tracker 子进程、Open3D 首帧全部带到可运行状态。它和 shape prior 不是一回事：普通 warmup 是 live run 的必要起跑动作，shape prior 是 额外生成 canonical reference 的单次任务。

两个 GPU 怎么分

Demo 3.2/3.3 默认 `--mask-gpu 0 --cotracker-gpu 1`。入口先让主进程只看 GPU0；tracker 用独立子进程和 `CUDA_VISIBLE_DEVICES=1` 跑在 GPU1。 两边通过 pickle/latest-wins IPC 传 RGB + mask input 和 tracker result， 不做跨 GPU CUDA tensor transfer。

Warmup B

Shape prior warmup：先抓 snapshot，再 after-teardown 跑重路线

  1. 1第一组有效 strict-source tracking input 到达后，复制 RGB-D、object/controller mask、intrinsics、c2w。
  2. 2写出 FuturePhysTwin-style one-frame case：`color/`, `mask/`, `pcd/`, `calibrate.pkl`, `processed_masks.pkl`, `track_process_data.pkl`。
  3. 3默认状态变成 `case_ready`，heavy route 不阻塞 tracker input，也不阻塞第一帧 render。
  4. 4live process teardown 后，detached completion worker 等 GPU 内存释放再执行五段 route。
  5. 5读取 `final_data.pkl`，拼出 `object_points[0] + surface_points + interior_points`，作为灰色 reference layer。

Actual run

正式运行：严格同源 group_id 驱动一帧完整输出

Capture

三相机 RealSense 产生同一组 RGB/IR/depth 时间片。

Depth + Mask

GPU0 跑 FFS TensorRT batch=3 depth，然后 SAM3.1/HF EdgeTAM 给 object/controller mask。

Tracker

GPU1 tracker 子进程收到 RGB + trackable masks，返回 tracks、visibility 和语义归属。

Render

主进程要求 tracker result 与 RGB/depth/mask 同 group，再 lift 3D markers 并送 Open3D。

Second pass

Actual run 的另一遍：用 visualizer 做诊断展示，不走 realtime_phystwin 主程序

输入是什么

visualizer pass 消费已经得到的视频帧、tracks、visibility 和可选 segm_mask。 它的职责是画轨迹点、轨迹线、可见性和遮罩后的颜色，再保存 mp4 或写到 writer。

它不做什么

它不重新启动完整 realtime_phystwin / PhysTwin physics pipeline， 不训练 spring-mass，不做 inverse physics，也不改变 Demo 5.1 的 live GPU ownership。这里它是 actual run 后的解释/检查视图。
